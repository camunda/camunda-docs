title: "Process instance suspension"

Process instance suspension lets you temporarily freeze a running process instance without canceling it. The instance retains all its state during suspension, and execution continues from the same point when you resume it.

Common use cases include:

- Pausing execution while an upstream or downstream system is unavailable or misconfigured.
- Preventing jobs from being picked up during a planned maintenance window.
- Temporarily halting a batch of instances while an investigation is in progress.

:::note
Suspension is not a substitute for cancellation or deletion. The instance continues to occupy cluster resources during suspension, including storage for any buffered commands.
:::

## Suspend and resume a process instance

Use the REST API to suspend or resume a single process instance:

- [Suspend a process instance](/apis-tools/orchestration-cluster-api-rest/specifications/suspend-process-instance.api.mdx)
- [Resume a process instance](/apis-tools/orchestration-cluster-api-rest/specifications/resume-process-instance.api.mdx)

You can also suspend or resume multiple instances at once with batch operations:

- [Suspend process instances (batch)](/apis-tools/orchestration-cluster-api-rest/specifications/suspend-process-instances-batch-operation.api.mdx)
- [Resume process instances (batch)](/apis-tools/orchestration-cluster-api-rest/specifications/resume-process-instances-batch-operation.api.mdx)

A suspended process instance appears in search results with a `SUSPENDED` state. Filtering for `ACTIVE` instances does not include suspended instances.

## How suspension works

When a process instance is suspended, the engine classifies every incoming command as one of the following:

- **Execute**: The command is processed immediately. Commands that terminate the instance (cancellation) fall in this category.
- **Buffer**: Internal follow-up commands generated by the engine are queued. They are not executed until the instance resumes.
- **Reject**: External triggers that would advance execution (signal triggers, job activations) are discarded.

On resume, the engine drains the buffer in order and continues normal execution.

### Jobs

Jobs belonging to suspended process instances are **parked**. Job workers do not pick them up. When the instance resumes, parked jobs are re-activated and become available to workers.

Secret resolution does not unpark jobs for suspended instances.

### Timers

Timers are not triggered during suspension. When the instance resumes, due timers fire immediately as a **catch-up**. For non-interrupting cycle timers, the engine fires the timer once for each missed interval until the next due date is in the future. This may produce N firings in rapid succession on resume.

### Messages

Message subscriptions are removed when the instance is suspended and re-created on resume.

Message correlation does not happen during suspension. Messages **without a TTL** that arrive while the instance is suspended are discarded for that instance. Messages **with a TTL** may still correlate after resume, provided the TTL has not expired at the time the subscription is re-created.

### Signals

Signal subscriptions are removed when the instance is suspended. Signals received during suspension are discarded and will never be replayed. Unlike timers, there is no catch-up mechanism for signals.

### Multi-instance

If the instance is suspended while a multi-instance body is active, child elements are spawned according to the **input collection at the time of suspension** when execution resumes. Items added to the collection during the suspension window are not included.

### Call activities

Suspending a root process instance does **not** automatically suspend its call-activity children. Each child instance continues executing independently.

If an active call activity has an interrupting boundary event, the child instance may fire a matching event (for example, an error or escalation) while the parent is suspended. In this case:

- The call activity element transitions to `TERMINATED`, even though the parent instance is suspended.
- The boundary event element instance is created, and its completion is buffered until resume.

This means a suspended process instance may have no active token until it resumes and the buffer drains.

## Variables

You can update variables on a suspended process instance. This includes element-instance variables, with one exception: **user task variables cannot be updated** during suspension because updating them would trigger a `UPDATING` task listener.

:::note
Variable changes made during suspension take effect immediately. If a buffered command was generated before suspension and depends on a variable you modified or deleted, it may fail on resume and create an incident.
:::

## Impact on Connectors

**Inbound connectors** publish messages to correlate with waiting process instances. Because message correlation is suppressed during suspension, data arriving from an inbound connector while the instance is suspended is not delivered to that instance and is permanently lost.

**Outbound connectors** execute as service task jobs. Those jobs are parked during suspension. Because Zeebe provides at-least-once delivery guarantees, an outbound connector that had already started work before suspension but did not complete it may execute again when the job is re-activated on resume. If the connector's action is not idempotent (for example, sending a message, charging a card), it may be executed more than once.

## Batch operations

You can suspend or resume multiple process instances using batch operations. Keep in mind:

- Batch operations that are already queued (for example, a cancel or migrate batch) and target process instances that are subsequently suspended may fail on individual items if the instance state is incompatible with the queued operation.
- Batch operations for suspend and resume report item-level results. An individual item failure does not stop the rest of the batch.

## Storage impact

Buffered commands are stored on the broker's persistent volume (PVC). A process instance with many active tokens or long-lived subscriptions generates more buffered commands during suspension. Monitor PVC utilization when suspending large numbers of instances or instances with complex execution states.

## Resume behavior and limitations

When a process instance resumes, the engine drains all buffered commands in the order they were recorded. During the drain:

- The instance is visible as `ACTIVE`, but execution has not yet completed the catch-up.
- A re-suspension request while a drain is in flight is rejected. You must wait for the drain to complete before suspending again.

In rare cases, a buffered command cannot be drained — for example, if a preceding command (such as a variable modification permitted during suspension) left the instance in an inconsistent state for the buffered command to process. This typically creates an incident. In very rare cases, a drain failure may not surface as an incident, leaving the instance in an inconsistent state without visible indication. If a resumed instance stops progressing unexpectedly, check the instance for incidents and compare its current state against the expected element progression.

## Process instance modification during suspension

You can apply process instance modification to a suspended instance. Modification commands are executed immediately and are **not** buffered. However, modifications run interleaved with the buffered command queue, meaning:

- A modification may activate an element whose follow-up commands are then interleaved with already-buffered commands on resume.
- If modification removes or terminates an element that has buffered commands, those commands may fail on drain and create incidents.

Use [modification](./process-instance-modification.md) on suspended instances with care.
